## 1.5. Workspace synthesis (clean-machine smokes only)

Step 7's "Settings → Version reads N+1" assertion requires a connected workspace — clean-machine helpers show only `Connect your Taproot account` + `Quit` in the menu (no Settings row), so the assertion can't be checked.

If you don't have a real workspace connected (e.g. B3 cloud signin not yet deployed), synthesize one:

```bash
UUID="$(uuidgen)"
# 1) Plant a bearer in Keychain matching the loadWorkspacesFromKeychain shape.
security add-generic-password \
  -s "com.taproot.helper" \
  -a "workspace.${UUID}.bearer" \
  -w "smoke-bearer-token-not-real" \
  -U
# 2) Plant the workspace name + vault folder in UserDefaults.
mkdir -p "$HOME/Documents/Taproot/smoke-vault"
defaults write com.taproot.helper "taproot.workspaceName.${UUID}" -string "Smoke Vault"
defaults write com.taproot.helper "taproot.vaultFolder.${UUID}" -string "$HOME/Documents/Taproot/smoke-vault"
echo "$UUID"   # save this — needed for cleanup
```

`AppDelegate.loadWorkspacesFromKeychain` picks this up at next launch and the menu now shows Settings + a workspace row. The bearer is intentionally invalid — sync calls will 401, but the auto-update flow we're testing doesn't depend on the cloud round-trip.

To clean up after the smoke:

```bash
security delete-generic-password \
  -s "com.taproot.helper" \
  -a "workspace.${UUID}.bearer" 2>/dev/null || true
defaults delete com.taproot.helper "taproot.workspaceName.${UUID}" 2>/dev/null || true
defaults delete com.taproot.helper "taproot.vaultFolder.${UUID}" 2>/dev/null || true
rm -rf "$HOME/Documents/Taproot/smoke-vault"
```

Skip this step entirely if you have a real workspace already connected.

## 2. Build staging N+1

In a temporary branch (do NOT commit version bumps to `main` until after smoke passes):

1. `Sources/TaprootHelper/Info.plist`: bump `CFBundleShortVersionString` (e.g. `0.1.1` → `0.1.2`) and `CFBundleVersion` (e.g. `2` → `3`). Use surgical Edit, NOT `PlistBuddy Set` — `PlistBuddy` reformats the whole plist (4-space → tabs, key alphabetization) and creates a noisy diff.
2. Build + codesign + zip in one shot via `build-app.sh`:

   ```bash
   ./scripts/release/build-app.sh /tmp/staging-N+1 --zip
   ```

   The script: `swift build -c release` → assembles `TaprootHelper.app` (Info.plist + executable + Sparkle.framework) → adds `@executable_path/../Frameworks` rpath via `install_name_tool` → inside-out Developer ID codesign (Sparkle XPC services + Updater.app + Autoupdate + framework + outer .app) → zip via `ditto -c -k --keepParent`. Output: `/tmp/staging-N+1/TaprootHelper.app` + `/tmp/staging-N+1/TaprootHelper-N+1.zip`.

   Override the codesign identity with `TAPROOT_CODESIGN_IDENTITY=<sha>` if needed (default: Tom's Developer ID `BC24E4A647583D1B567D8A0CD3DFBE74C3A2C522`).

## 4. Publish staging artifacts

Run the wrangler commands `sign-and-publish.sh` printed (it does NOT execute them — operationally safer). Note the `--remote` flag on the r2 put — it's required:

```bash
# 1. Upload signed zip to R2 — `--remote` is REQUIRED.
#    Without it, wrangler writes to the local miniflare simulator only
#    and the canonical R2 URL stays 404. The smoke discovered this the
#    hard way; `sign-and-publish.sh` now prints the flag.
wrangler r2 object put taproot-releases/releases/v0.1.1/TaprootHelper-0.1.1.zip \
  --file=/tmp/staging-N+1/TaprootHelper-N+1.zip \
  --content-type=application/octet-stream \
  --remote

# 2. Deploy appcast to a Pages preview (staging)
wrangler pages deploy ./scripts/release/out --project-name=taproot-updates
```

Wrangler emits a per-deploy preview URL like `https://<commit>.taproot-updates.pages.dev/appcast.xml`. **Copy that URL** — it's your staging feed for step 5. The `taproot-updates-staging.pages.dev` static slug from the original parent plan does not exist; preview URLs are per-deploy only.

> **Cloudflare edge cache 404-poison gotcha (smoke finding).** If anyone (curl, browser, prior smoke run) HEAD/GETs the canonical R2 URL `https://downloads.taproothq.com/releases/v<short>/TaprootHelper-<short>.zip` BEFORE step 4.1 completes the upload, Cloudflare's edge will cache the 404 (`max-age=14400` = 4 hours) and the upload won't be visible at the canonical URL until cache expiry. The smoke worked around it by waiting ~30 minutes for natural eviction by step 10 — not a workflow you want to repeat. Mitigations:
>
> - **Pre-warm correctly:** run step 4.1 (`wrangler r2 object put --remote`) BEFORE any HEAD/GET against the canonical URL. Sparkle's first check on step 6 will then hit a populated cache.
> - **Cache-bust the staging enclosure URL:** after step 4.2, sed the appcast `<enclosure url="...">` to append `?v=<token>` (any unused token). The appcast itself ages out of cache fast (no canonical URL), so re-deploys with new tokens always work.
> - **API-purge the canonical URL:** `curl -X POST https://api.cloudflare.com/.../purge_cache -d '{"files":["https://downloads.taproothq.com/releases/v<short>/TaprootHelper-<short>.zip"]}'` if you have an API token configured. Heaviest hammer.

## 8. Edge-case smokes

### 8a. Silent background download (Sparkle still surfaces the Install prompt)

```bash
# The SettingsStore key — NOT `SUAutomaticallyUpdate`.
# UpdateCoordinator.start() overwrites SUAutomaticallyUpdate at every
# launch from this key (smoke finding). The SU* key is therefore
# functionally read-only from the user's perspective; persisting state
# requires the SettingsStore key.
defaults write com.taproot.helper "taproot.settings.automaticallyDownloadsUpdates" -bool YES
```

Quit + relaunch helper. Trigger another update (re-publish a staging N+2 via steps 2–4, or just re-deploy with a fresh preview URL).

> **Sparkle's standard UI shows the Install prompt regardless of `automaticallyDownloadsUpdates`.** The cycle-11 smoke note diagnosed strict 8a "no dialog ever" as a missing wiring; that diagnosis was wrong. Verified against `Sparkle.xcframework/.../SPUUpdater.h`: Sparkle 2 has only `automaticallyChecksForUpdates`, `automaticallyDownloadsUpdates`, `updateCheckInterval`, and `feedURL` — there is no `automaticallyInstallsUpdates` property. `SparkleUpdaterService` already routes our settings-key value into Sparkle's actual `automaticallyDownloadsUpdates` (post sub-scope B rename, the names finally match).
>
> Setting `automaticallyDownloadsUpdates=YES` causes Sparkle to download the update silently in the background, then surface its standard "Update available" prompt anyway — that prompt is `SPUStandardUpdaterController`'s standard UI driver behavior, not gated by any property. **Suppressing the prompt requires implementing a custom `SPUUserDriver`, deliberately not in Stage 1** per the 2026-05-01 UX call (Standard Sparkle prompt is the intended Stage 1 UX; see [[2026-05-01-taproot-t11.8-execution-shipped]] §sub-scope B).

What to verify:

- [ ] No download progress dialog appears (Sparkle pulls the zip in the background).
- [ ] When download completes, Sparkle surfaces the standard "Update available" prompt — this is expected.
- [ ] Click Install Update → no further confirmation dialog (post-download "Ready to install" stage is suppressed by `automaticallyDownloadsUpdates=YES`).
- [ ] Helper terminates and relaunches at the new version; relaunch respects `shouldPostponeRelaunchForUpdate` (if a push is in flight, helper waits for it).
